[.lead]
Migrate applications to the cloud
****
This workshop is about migrating applications to the cloud.
It is based on the Konveyor framework, which:

* analyzes (Java) applications for cloud readiness, and
* supports the migration of (Java) applications to the cloud.

We use **Konveyor Hub** for application analysis and **Konveyor AI** (VS Code extension) for AI-assisted migration.
We concentrate on Java
and use a simple example application to demonstrate the migration process.
The principles and tools can be applied to other languages and applications as well (with some limitations).

[NOTE]
====
https://konveyor.io/[Konveyor] is a community-driven project that aims to help organizations modernize their applications and infrastructure.
It is part of the https://www.cncf.io/[Cloud Native Computing Foundation (CNCF)].
====
****

== Exercises

=== Exercise 1: Run a (scaled) Spring PetClinic application

==== Start with initial application

. Start the Spring PetClinic application in a container.
+
[source, bash]
----
docker compose up -d
----

. Upload some images (cf. link:scripts/upload-dummy-image.sh[upload-dummy-image.sh]).
+
[source, bash]
----
./scripts/upload-dummy-image.sh
# -> Image uploaded successfully
----

. List the uploaded images (cf. link:scripts/list-images.sh[list-images.sh]).
+
[source, bash]
----
./scripts/list-images.sh
# -> Image list: ...
----

==== Scale up

. Now, scale the application to more (>= 2) replicas.
+
[source, bash]
----
docker compose up -d --scale petclinic=2
docker compose restart nginx # necessary to update the load balancer
----

. List the uploaded images again.
You should see that the images are distributed across the replicas.
Either

** You get the list as before:
+
[source, bash]
----
./scripts/list-images.sh
# -> Image list: ...
----
** Or, you get an empty list:
+
[source, bash]
----
./scripts/list-images.sh
# -> []
----

. If you add more images, you will even see that they are distributed across the replicas.

[NOTE]
====
This demonstrates a common cloud-readiness issue: the application stores files on the local filesystem.
When scaled to multiple replicas, each replica has its own filesystem and uploaded files are not shared.
In the next exercises, we will use Konveyor to analyze and address such issues.
====

=== Exercise 2: Install Konveyor Hub and Analyze the Application

In this exercise, we install Konveyor Hub on a Kubernetes cluster,
explore its features, and run an analysis of the Spring PetClinic application.

==== Enable ingress (minikube only)

If you are using minikube, enable the ingress addon so the Konveyor Hub UI
can be exposed later:

[source, bash]
----
minikube addons enable ingress
----

For Docker Desktop / Rancher Desktop, use their built-in ingress or
`kubectl port-forward` (see link:#_access_the_konveyor_hub_ui[Access the Konveyor Hub UI] below).

==== Install Konveyor Hub with the provided script

The repository ships a script that automates the full Konveyor Hub installation:

* installs the Operator Lifecycle Manager (OLM),
* applies the Konveyor operator manifest from link:scripts/konveyor-hub/konveyor-operator-stable.yaml[`scripts/konveyor-hub/konveyor-operator-stable.yaml`] (stable channel),
* waits for the operator and its CRDs to become ready, and
* creates the Tackle custom resource from link:scripts/konveyor-hub/tackle-instance.yaml[`scripts/konveyor-hub/tackle-instance.yaml`].

[IMPORTANT]
====
Konveyor requires a storage class that supports RWX (ReadWriteMany) volumes.
Review your cluster's storage capabilities before proceeding.

If you use Rancher Desktop, edit link:scripts/konveyor-hub/tackle-instance.yaml[`tackle-instance.yaml`]
and change `ui_ingress_class_name` from `nginx` to `traefik` before running the script.
====

Run the script from the `scripts/` directory (it references its resources via relative paths):

[source, bash]
----
cd scripts
./install_konveyor_hub.sh
cd ..
----

[TIP]
====
The script pins the OLM version (`OLM_VERSION`) and the Konveyor release channel
(`KONVEYOR_VERSION`, defaulting to `stable`) at the top of the file.
Edit these values if you need a different version or the `alpha` channel.

For released versions you can alternatively install via https://operatorhub.io/operator/konveyor-operator[OperatorHub].
For more details, see the https://github.com/konveyor/operator/blob/main/README.md[Konveyor Operator README].
====

==== Verify the Deployment

Deployment typically takes 1-3 minutes. Check the status:

[source, bash]
----
kubectl get pods -n konveyor-tackle
----

You should see pods for the following components:

* `konveyor-tackle`
* `tackle-hub`
* `tackle-keycloak-postgresql`
* `tackle-keycloak-sso`
* `tackle-operator`
* `tackle-ui`

==== Access the Konveyor Hub UI

Access the UI in your browser.

.For minikube
[source, bash]
----
echo "http://$(minikube ip)"
----

.For Docker Desktop / Rancher Desktop
Access via `http://localhost` (if ingress is configured) or use `kubectl port-forward`:
[source, bash]
----
kubectl port-forward svc/tackle-ui -n konveyor-tackle 8080:8080
# Then open http://localhost:8080
----

==== Explore Konveyor Hub Features

Take some time to explore the Konveyor Hub UI:

. **Application Inventory** — Add and manage applications to be analyzed.
. **Assessment** — Assess applications for cloud readiness using questionnaires.
. **Analysis Configuration** — Configure analysis targets and rules.

==== Add and Analyze Spring PetClinic

. Navigate to the **Application Inventory** in the Konveyor Hub UI.
. Use the **Create New** button to add the Spring PetClinic application:
** Set a name (e.g., "Spring PetClinic").
** Provide the repository URL under the *Source Code* section: `https://github.com/konveyor-demos/spring-petclinic-ec26`
** Set the branch to `workshop`.
. Select your created application and use the **Analyze** button to run an analysis:
** Keep everything as default, except setting the targets
** Select the appropriate targets, for our Cloud Readiness checks:
*** Containerization
*** Azure -> Azure Kubernetes Service
*** For the Spring Boot 3 migration, you can also the Spring and Java related targets
** Continue with the menu and click **Run**.
. Wait for the analysis to finish (this can take around 5-10 mins) and review the analysis report.
** Identify cloud-readiness issues, particularly the local filesystem access pattern.
** Note the issues that will need to be addressed for cloud migration.

=== Exercise 3: Migrate to Spring Boot 3 with Konveyor AI

In this exercise, we use the Konveyor AI VS Code extension to analyze the application
and perform an AI-assisted migration from Spring Boot 2 to Spring Boot 3.

==== Install Konveyor AI in VS Code

. Open VS Code.
. Go to the Extensions marketplace (`Ctrl+Shift+X` / `Cmd+Shift+X`).
. Search for **"Konveyor"** and install the extension.
. Open the Command Palette (`Ctrl+Shift+P` / `Cmd+Shift+P`) and run:
+
----
Welcome: Open Walkthrough
----
+
Follow the Konveyor setup walkthrough to complete the initial configuration.

[TIP]
====
For detailed installation instructions, see the
https://github.com/konveyor/editor-extensions/blob/main/vscode/core/README.md[Konveyor VS Code Extension README].
====

==== Configure GenAI

Now open the sample project in VS Code.

Set up your AI provider to enable AI-powered migration suggestions:

. Go to the new Konveyor component on the left side of VS Code
. Click **Open Analysis panel**
. Click on the settings wheel on the top right of the Analysis panel
. Use **Configure GenAI settings** to set up your AI provider and API key
** In the sample configuration, search for your provider (e.g., OpenAI, Anthropic, Azure OpenAI, Ollama, etc.).
** Check if you already have an API key for any of the above providers, if not let the workshop instructor know.
** Enter your API key or credentials.

*Example Configurations:*

ChatGPT (OpenAI):

[source, yaml]
models:
  OpenAI: &active
    environment:
      OPENAI_API_KEY: "" # Required - either set here or in your environment variables
    provider: ChatOpenAI
    args:
      model: gpt-5.4 # Required

Claude API:

[source, yaml]
models:
  OpenAI: &active
    provider: ChatOpenAI
    environment:
      OPENAI_API_KEY: "" # Required - either set here or in your environment variables
    args:
      model: claude-sonnet-4-6 # Required
      configuration:
        baseURL: "https://api.anthropic.com/v1/"

Ollama:

[source, yaml]
models:
  ChatOllama: &active
    provider: ChatOllama
    args:
      model: gemma4:31b # example using Gemma 4, adjust to your installed model
      baseUrl: "http://localhost:11434" # Required

[NOTE]
====
Recommended models for local LLM execution include:

* https://ollama.com/library/gemma4[Gemma 4]
** `gemma4:31b` - needs > 31 GB of RAM, so recommended for 64 GB RAM machines
** `gemma4:e4b` - a smaller version of the above, needs ~ 10 GB of RAM, so recommended for 32 GB RAM machines
* https://ollama.com/library/glm-4.7-flash[GLM 4.7 - Flash] - `glm-4.7-flash:latest` - needs 20 GB of RAM, so recommended for 64 GB RAM machines
====

==== Configure Hub Configuration

We can also configure a connection to our deployed Konveyor Hub to support solution generation and profile sharing.

. Inside the settings panel, select **Configure Hub Settings**
. Under Hub URL, enter the URL to your Konveyor Hub instance (e.g., `http://localhost:8080` or `http://<minikube-ip>` or `http://localhost`).
. Keep the defaults and save the settings using the **Save** button.
. There should be a confirmation message that the connection was successful.

==== Create an Analysis Profile

. Open the **Konveyor Analysis View** in the VS Code sidebar.
. Open the profiles dropdown and select **"Manage Profiles"**.
. Click **"+ New Profile"**.
. Add the following target technologies:
** `cloud-readiness`
** `jakarta-ee`
** `jakarta-ee9`
** `java-ee`
** `openjdk17`
** `spring-boot3+`
** `spring-security6+`

[TIP]
====
You can also add custom rulesets if you have specific migration rules for your organization.
====

==== Run Analysis

. In the Konveyor Analysis View, start the **analysis server** by clicking the **Start** button at the top of the view.
. Select your created profile and click **"Run Analysis"**
. Wait for the analysis to complete and review the detected issues.

Expected issues include:

* Spring Boot version not compatible with Jakarta EE 9+
* `javax` packages need to be replaced by `jakarta`
* Deprecated Spring Security configuration patterns (if applicable)

==== Apply Migration Fixes with AI

For each detected issue, use the Konveyor AI to generate and apply fixes:

. **Spring Boot Version**
** Click the tool icon next to the Spring Boot version issue.
** Review the AI-suggested changes (e.g., Boot 2.x → 3.x, Java version → 17).
** Accept the suggested fix.

. **javax → jakarta Migration**
** Select the package migration issues.
** Review the suggested import changes (e.g., `javax.servlet` → `jakarta.servlet`).
** Accept the changes across all affected files.

. **Spring Security Configuration**
** Review suggestions for migrating deprecated patterns
(e.g., `WebSecurityConfigurerAdapter` → bean-based `SecurityFilterChain`).
** Accept the changes.

[NOTE]
====
After each fix is applied, the analysis may re-run automatically to update the remaining issues.

You should also see that after applying one fix, the next fix of the same issue loads the solution from the Hub (if connected) instead of generating a new one, demonstrating the reuse of solutions across issues and projects. While the LLM is still triggered, the RAG approach leads to a faster response time and more consistent solutions.
====

==== Verify the Migration

[CAUTION]
.Switch to Java 17 (or higher)
====
After the migration to Spring Boot 3, you need Java 17 to build and run the application.
====

After applying all fixes, verify that the application builds and runs correctly:

[source, bash]
----
./mvnw clean install
----

You should see a successful build output. Then run the application:

[source, bash]
----
./mvnw spring-boot:run
----

=== Exercise 4 (Bonus): Migrate from local File Access to Storage Service

Though we now have switched to the current Spring Boot 3,
the application is still working with a local file store
as found out in the analysis of the previous exercises.
This requires an architectural change (re-architect).
We would like to store the files in a respective storage service
as provided by the underlying cloud provider or platform.

As we will not use a real cloud provider in the workshop,
we propose to use a local implementation of AWS S3 with https://github.com/ministackorg/ministack[Ministack].

Whatever solution you choose, it most probably affects the following parts of your implementation:

* Cloud Stack (local link:docker-compose.yml[Docker compose] file).
* Configuration (link:src/main/resources/application.properties[application properties], perhaps Spring profiles).
* Dependency management (link:pom.xml[Maven configuration]).
* Implementation (of at least link:src/main/java/org/springframework/samples/petclinic/images/ImageController.java[ImageController],
beyond switching the underlying storage, you may have to introduce further configurations, tests etc.).
* You can try to use Konveyor AI to assist you in the migration, but you can also do it with an AI agent of your choice, e.g. Claude Code.
